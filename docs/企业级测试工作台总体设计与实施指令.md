# TestMaster 企业级测试工作台总体设计与实施指令

| 项目 | 内容 |
|---|---|
| 版本 | v2.0 |
| 日期 | 2026-07-24 |
| 定位 | 面向测试团队的桌面优先统一测试工作台 |
| 技术基线 | Electron + Vue 3 + FastAPI + PostgreSQL + Playwright |
| 实施原则 | 先闭环、后扩展；先真实执行、后展示页面；每项功能必须可验收 |

## 1. 产品定位

TestMaster 不应复制 Apifox 或 ApiPost 的接口调试页面，也不应只是把网页套进 Electron。产品应成为测试人员日常使用的统一工作台：用真实流量建立接口资产，用真实环境执行 API/UI/混合场景，用统一数据、Mock、环境、报告和通知完成回归闭环。

核心用户路径：

```text
需求/接口文档/真实流量
  -> 接口资产与页面对象
  -> 测试数据准备
  -> API、UI 或混合场景编排
  -> 本地调试 / Agent / CI 执行
  -> 产物、诊断、缺陷、通知、趋势
  -> 需求与版本质量追溯
```

桌面端是测试人员的操作台、浏览器执行器、受控流量采集器和本地 Agent；服务端是资产、执行状态、调度、报告和协作的唯一事实来源。

## 2. 不可妥协的设计原则

1. 任何按钮必须有真实数据来源、真实动作和成功/失败反馈；禁止只弹出“已执行”或填充模拟数据。
2. 任何新增能力必须具备完整闭环：数据模型、迁移、权限、API、前端入口、真实执行器、日志/产物、自动化测试。
3. 同一个概念只能有一个权威模型。例如项目、环境、执行记录、产物、变量、Agent 不得另建平行体系。
4. 页面不能替代能力。没有执行器或调度器支持的配置，不得在 UI 宣传为“已支持”。
5. 状态变化必须可追溯、可恢复、可重试，不能因桌面退出、网络短断、服务重启而永远停留在 `running`。
6. AI 只能给建议、归纳和生成候选；涉及修改定位器、正式用例、生产数据时必须由人确认并产生版本记录。
7. 以 PostgreSQL 迁移为唯一数据库升级方式；不以 `create_all()`、本地 JSON 或 SQLite 作为线上权威存储。
8. 不实现绕过验证码、TLS Pinning、证书校验或应用保护的能力。App/小程序流量通过合规代理配置、设备授权或 HAR 导入接入。

## 3. 信息架构和桌面端导航

桌面端首屏不是自动化总览大杂烩。采用工作区导航，默认进入“工作概览”，每个工作区只显示与当前任务有关的命令。

| 工作区 | 一级页面 | 主要任务 |
|---|---|---|
| 概览 | 工作概览、执行队列、通知 | 今日任务、环境/Agent 状态、失败回归、快捷入口 |
| API 资产 | 接口调试、接口目录、文档同步、历史 Diff、代码生成 | 设计、调试、导入、版本化 API |
| 自动化 | API 用例、场景、套件、数据驱动、健康监控、契约测试 | 构建和执行接口回归 |
| UI 自动化 | UI 用例、录制、元素仓库、视觉回归、Trace、网络规则 | 浏览器端到端测试与维护 |
| 流量与 Mock | 浏览器流量、HAR 导入、代理抓包、导入中心、Mock 服务 | 从真实流量建立测试资产 |
| 执行与报告 | 执行历史、分片进度、报告、Flaky、缺陷、CI | 观察、治理、交付质量结果 |
| 管理 | 项目、环境、变量、测试数据、Agent、通知、集成 | 配置团队运行基础设施 |

导航规则：一级工作区最多 7 个；同类能力只保留一个入口；“新建”“导入”“运行”置于页面工具栏右上；编辑器内操作置于编辑器顶部或上下文菜单，不把核心操作藏在左侧树底部。

## 4. 统一领域模型

### 4.1 项目和资产归属

新增或补齐真正的 `Project` 模型，不得继续以 `user_id` 伪装 `project_id`。所有以下数据都必须带 `project_id` 并在查询、写入、导入、执行时验证归属：接口、接口分组、环境、变量、场景、套件、UI 用例、元素、流量、Mock、数据集、执行、报告、缺陷、需求、通知渠道、Agent 绑定关系。

```
Organization (可选，首期可单组织)
  Project
    Environment / VariableSet / SecretReference
    ApiDefinition / ApiCase / Scenario / Suite
    UICase / UIPage / UIElement / UISuite
    Dataset / DataProvider / DataLifecycle
    MockRule / CaptureSession / ImportJob
    AutomationExecution / ExecutionItem / ArtifactManifest
    Requirement / Review / Defect / ReportTemplate
```

### 4.2 统一执行模型

`AutomationExecution` 是唯一权威执行父记录；`ExecutionItem` 表示 API 用例、场景、UI 用例、UI 分片、性能计划等成员。UI 子分片不得把自身当成独立业务回归结果，必须汇总到父执行。

状态机：

```text
queued -> waiting_for_agent -> assigned -> running -> passed
                                              -> failed
                                              -> cancelled
                                              -> timed_out
                                              -> infra_error
```

要求：每次状态迁移写入事件；取消、超时、重试都有独立 attempt；父任务只有所有成员终态后才终态；通知只针对最终父任务发送一次。

### 4.3 变量和测试数据

变量分为：项目变量、环境变量、密钥引用、运行时变量、数据行变量。优先级必须固定为：运行时参数 > 数据行 > 场景提取值 > 环境变量 > 项目变量 > 默认值。

测试数据不能只有 Faker。增加 `DataLifecycle`：

| 阶段 | 能力 |
|---|---|
| Before Suite | 调 API/SQL/脚本准备数据，记录创建对象 |
| Before Case | 数据行绑定、幂等创建、租约占用 |
| After Case | 释放、删除、回滚、失败补偿 |
| After Suite | 清理残留、输出数据审计 |

数据提供者首期：CSV、JSON、Excel、内置生成器、HTTP 前置调用、SQL 查询。SQL 连接采用已保存连接配置和参数化查询，结果可作为变量或断言来源。

## 5. API 资产与自动化设计

### 5.1 接口资产必须达到的能力

接口不是一个散落的 URL 表。`ApiDefinition` 至少保存：目录、方法、路径模板、请求参数模型、请求/响应 Schema、示例、鉴权配置、标签、版本、来源、最后同步时间、关联用例和变更影响。

支持 OpenAPI 3.x、Swagger 2.0、Postman v2.1、cURL、HAR、Apipost 导入。导入流程固定为：解析 -> 标准化候选 -> Diff/冲突预览 -> 用户确认策略 -> 单事务落库 -> 导入审计。禁止导入即覆盖正式资产。

OpenAPI 同步：可配置来源 URL 和轮询时间；每次创建不可变快照；Diff 输出新增、删除、兼容变更、破坏性变更；自动标记受影响接口、用例、场景和契约规则；用户可选择创建修复任务或阻断发布。

### 5.2 接口调试器

调试器应有：请求构建、环境选择、变量预览、鉴权助手、Cookie 会话、请求历史、响应 Pretty/Raw/Headers、响应 Diff、断言试运行、保存为接口/用例/场景步骤、导出至少 12 种语言代码。

接口协议作为一等资产：

| 协议 | 首期交付标准 |
|---|---|
| HTTP/HTTPS | 请求、断言、变量提取、套件、历史、导入 |
| gRPC | Proto 上传/版本、反射、Unary/Server Streaming 调试、保存用例、断言、套件执行 |
| WebSocket | 连接、鉴权、发送、收包序列、超时、断言、关闭、保存用例 |
| SSE | 订阅、事件筛选、事件数量/字段断言、超时、取消 |
| MQTT | 仅物联网项目启用；连接、发布、订阅、QoS、断言 |

所有协议用例必须能作为场景步骤，而不是只存在一个“调试页”。

### 5.3 接口场景 DSL

场景不能只是线性列表。底层 DSL 必须支持顺序、条件分支、循环、并行块、子场景、重试、等待、补偿、前后置钩子、数据驱动、API/UI 混合步骤。可视化流程图是 DSL 的编辑器，不是另存一套无法执行的 JSON。

API/UI 混合示例：`API 创建订单 -> 浏览器打开订单页 -> 断言页面显示 -> UI 完成支付 -> API 校验订单状态 -> 数据清理`。

### 5.4 断言、契约和健康监控

断言类型：状态码、Header、Cookie、JSONPath、JSON Schema、响应时间、正则、集合、数据库、消息队列、文件存在、视觉断言、业务表达式。

契约规则必须在以下四条链路自动执行：接口调试的“运行断言”、单接口用例、场景步骤、套件/CI。任一路径失败都必须将契约错误写进步骤结果和最终报告。

健康监控从已验证接口用例和环境解析真实请求，支持定时、阈值、连续失败、延迟劣化、告警恢复。多实例通过数据库租约只允许一个实例执行同一检测；仪表盘展示可用率、P95、错误分布、趋势和事件时间线。

## 6. UI 自动化设计

### 6.1 执行能力

使用 Playwright，不使用 Selenium。浏览器矩阵为 Chromium、Firefox、WebKit，所有用例默认 Chromium，可按套件选择矩阵。每个矩阵成员独立 Context、独立存储态、独立视觉基线。

步骤覆盖：导航、点击、填写、选择、上传、下载、拖拽、键盘、滚动、悬停、等待、断言、脚本钩子、截图、网络 Mock、标签页/弹窗、iframe、Shadow DOM、权限、验证码人工暂停。

默认同步只用 Playwright 的可见、可操作、导航、网络空闲、业务元素等待；禁止把固定 `sleep` 当作默认方案。需要固定等待时，必须显式以步骤形式显示。

### 6.2 录制与可维护性

录制器产出结构化步骤，不保存坐标脚本。定位器优先级：`data-testid > role + accessible name > label > placeholder > text > css > xpath`。每个步骤保存候选定位器、唯一性结果、页面 URL、frame 路径和录制证据。

元素仓库/POM 是真实执行数据源：用例步骤保存 `element_id`；执行前解析仓库定位器；仓库更新后可展示受影响用例并在沙箱 dry-run；所有修改创建版本，支持回滚。

自愈只能在当前运行临时使用高置信候选；永久变更必须由用户在“自愈历史”审核后确认。审核前不得修改共享元素。

### 6.3 视觉、Trace 和网络规则

视觉回归以 `project + case version + step + browser + viewport + color scheme` 定位基线。首次基线、审批提升、回滚、遮罩、阈值、Diff 图均可追溯。不同浏览器或分辨率不得共用基线。

Trace Viewer 应直接展示操作时间线、截图、DOM 快照、控制台、网络瀑布、错误定位和可下载原始 Trace；用户不需要自行执行 `npx playwright show-trace`。

网络规则支持匹配 URL/方法/资源类型，并按用例、套件、场景步骤、环境和执行次数启用。动作包括 fulfill、delay、abort、修改请求头、修改响应头、替换响应体、状态机顺序响应。每次命中写入执行日志。

## 7. 流量采集、导入与 Mock

### 7.1 三层采集模型

| 层级 | 范围 | 实现 |
|---|---|---|
| 浏览器采集 | TestMaster 启动的浏览器 | Playwright request/response 事件 |
| HAR 导入 | 用户已导出的浏览器或代理会话 | 本地解析、脱敏、预览、导入 |
| 合规代理采集 | 授权的桌面/模拟器/手机流量 | 本地代理服务、证书安装引导、设备代理配置、会话导出 |

代理采集必须明确显示当前状态、监听端口、证书状态、设备连接说明、域名过滤、数据保留策略。不得承诺或实现绕过 TLS Pinning。对无法解密的流量，保留连接元数据和 HAR/PCAP 导入提示，不伪造 HTTP 内容。

### 7.2 流量转资产

捕获流量必须先进入导入中心候选区，用户可选择：丢弃、转接口、合并到接口、转场景步骤、生成 Mock 规则。转换前展示脱敏结果、动态字段建议、依赖图和默认断言。

从登录到下单的链路必须由用户确认 token、订单 ID、时间戳、随机数等变量映射，生成后先在选择环境试运行成功，才标记为可回归场景。

### 7.3 Mock

Mock 分为固定响应、规则响应、状态机 Mock、故障注入。故障注入首期支持状态码、延迟、伪超时、无效 JSON、自定义 Header；规则命中、随机值、故障类型和 seed 全部写日志。传输层断连等高级故障仅在专用代理层实现并明确标注。

## 8. 执行、Agent、CI 与通知

### 8.1 执行位置

| 类型 | 推荐执行器 |
|---|---|
| API/契约/健康监控 | 服务端 Worker |
| 手工 UI 调试/录制 | 桌面端本地 Playwright |
| 无人值守 UI 回归 | 注册的桌面 Agent |
| 浏览器矩阵/大回归 | 多 Agent 分片 |
| 性能 | JMeter Worker 或专用性能节点 |

Agent 必须上报浏览器版本、可用引擎、并发槽位、标签、网络区域、当前任务。调度器根据项目、环境、标签、浏览器、容量和并发标签分配任务。

并发标签必须是运行时约束，不只是分片算法：以数据库/Redis 租约维护每个标签的占用槽位，`max_concurrent=N` 时任意时刻最多 N 个成员进入 `running`。同一用例多个标签取最严格限制。

### 8.2 CI/CD

提供稳定的 API/CLI：创建执行、传入环境和变量、查询状态、取消、下载 JUnit/Allure/HTML 报告。提供 Jenkins、GitLab CI、GitHub Actions 示例模板。

CI 运行必须支持门禁规则：失败用例、契约破坏、视觉未审批、健康阈值、Flaky 白名单、覆盖率阈值。最终状态只在所有分片和重试结束后回传。

### 8.3 通知和离线回传

通知渠道至少包括企业微信、钉钉、邮件、Webhook；消息内容包含项目、环境、执行摘要、失败链接、Trace/截图入口。使用持久 Outbox，发送幂等、可重试、可查看投递记录。

桌面 Agent 离线时持久化事件和产物队列；网络恢复后按幂等键上传；超过保留期或与服务器状态冲突时给出可操作提示，不能静默丢失。

## 9. 测试管理、缺陷与报告

需求、用例、执行、缺陷之间要形成可追溯关系。需求覆盖率必须按项目、版本、需求状态统计；不是只统计接口数量。

缺陷集成支持 Jira、禅道、TAPD 的可配置连接。失败建缺陷时自动附带环境、版本、步骤、请求响应脱敏摘要、截图、Trace、日志、重现链接。支持防重复指纹和状态回写。

报告分三层：

1. 执行报告：每一步、每个成员、产物、变量脱敏摘要、重试、分片。
2. 质量报告：通过率、耗时、失败类型、Flaky、视觉、契约、覆盖率趋势。
3. 管理报告：版本质量门禁、需求覆盖、环境可用性、发布建议，可按企业模板和 Logo 导出。

## 10. AI 能力的正确边界

AI 可用于：流量聚类为链路候选、动态参数识别、断言建议、失败根因建议、定位器候选、接口变更影响分析、报告摘要。

每个 AI 输出必须包含证据、置信度、未知项和下一步操作。任何“自动修复”先生成候选补丁，在沙箱试跑，人工确认后创建新版本。AI 不得读取未脱敏生产流量或直接执行外部破坏性操作。

## 11. 实施阶段和退出标准

### Phase A：基础统一（必须先完成）

- 真正的项目模型与资产归属迁移。
- 统一执行父子模型、状态机、事件、产物、通知 Outbox。
- 环境/变量/密钥优先级统一。
- 桌面导航重构为工作区，不再将所有页面塞进自动化总览。

退出标准：新建两个项目后资产不串；桌面退出/网络断开/服务重启后执行都可恢复或明确终态；父分片结果准确汇总。

### Phase B：接口专业化

- OpenAPI 同步、版本快照、影响分析、响应历史 Diff。
- 协议用例一等资产（HTTP、gRPC、WebSocket、SSE）。
- 契约在调试、单用例、场景、套件、CI 全链路执行。
- 数据生命周期、数据库/消息断言。

退出标准：从 OpenAPI 变更能定位受影响用例；单接口和场景都能阻断契约错误；执行可准备并清理测试数据。

### Phase C：UI 与流量闭环

- 录制、元素仓库、三浏览器矩阵、视觉基线、Trace Viewer、网络规则。
- 浏览器采集、HAR 导入、合规代理采集、流量转接口/场景/Mock。

退出标准：录制的登录-下单流程可经变量确认后重复运行；元素改动能分析影响；浏览器/设备流量可经预览转为受控资产。

### Phase D：企业执行治理

- Agent 池、运行时并发标签租约、分片调度、CI、外部通知、离线回传。
- 缺陷/需求闭环、质量看板、报告模板。

退出标准：多个 Agent 的任务不重复领取；限制资源不会超并发；CI 可等待最终结果；失败可在手机通知中直达产物。

### Phase E：增强与差异化

- MQTT/中间件扩展、性能节点、AI 辅助、跨项目模板市场。
- 移动端/原生自动化仅在独立可验收引擎后评估，不混入 Web UI 引擎。

## 12. 每项功能的强制验收模板

其他 AI 每做一个功能，必须同时提交：设计说明、数据库迁移、接口文档、前端交互、后端测试、桌面真实 E2E 测试、失败/异常测试、截图或测试报告。

最小验收场景：

1. 正常创建、编辑、执行、查看结果、删除/停用。
2. 空数据、非法参数、权限不足、重复提交、网络中断、服务重启、任务取消、超时。
3. 两个项目、两个环境、两个 Agent 并行，确认数据和结果不会串。
4. 真实公共 HTTP 服务或本项目测试服务，不允许只 Mock 自己的后端方法。
5. 对桌面功能必须使用 Electron 正式包或 `win-unpacked` 进行真实点击验收，不能只跑 Vue 页面。
6. 前端 `npm run build`、后端指定测试和相关 E2E 必须通过；不能以“页面可打开”替代验收。

## 14. 给实施 AI 的阶段任务顺序

不要让一个 AI 一次性改完全部内容。按以下顺序执行，每阶段由 Codex 审查后再进入下一阶段：

1. Phase A：项目模型、统一执行和桌面信息架构。
2. Phase B-1：接口资产、OpenAPI 同步、契约全链路。
3. Phase B-2：测试数据生命周期和数据库/消息断言。
4. Phase C-1：UI 维护能力和多浏览器矩阵。
5. Phase C-2：流量中心和合规代理采集。
6. Phase D：Agent 调度、CI、通知、报告和缺陷闭环。
7. Phase E：AI、性能与可选协议扩展。

每阶段只在上一阶段的自动化回归通过后开始。若发现现有逻辑与规范冲突，应先写最小可回滚迁移和兼容层，再切换调用方，不能直接替换线上数据路径。
